# 图谱智能应用平台方案 v3.0

> 日期：2026-11-08 ｜ 状态：待批准
> 核心变更：从「化工安全方案」升级为「通用平台 + 应用包」；回答"以后加财务、干部应用时，升级还是重开插件"

## 0. 一句话结论与概念校正

**知识图谱、链路推导、沙盘推演是通用能力；安全、设备、CRM、财务、干部都是应用。**

因此正确的问题是：**如何把 dsh-ontology 从"一个应用"升级为"承载多个应用的平台"**，而不是"为安全域再开一个插件"。

**结论：升级现有插件为平台，应用以「应用包（AppPack）」形式扩展；默认不为单个应用重开插件。**

| 你的设想                 | 在本方案中的定位            | 做法               |
| -------------------- | ------------------- | ---------------- |
| 化工安全（法规+设备+作业+评级+根因） | 应用包 #1              | 新增 AppPack，不重开插件 |
| 设备管理                 | 应用包 #2（可复用安全域的设备本体） | 新增 AppPack       |
| CRM                  | 应用包 #3              | 新增 AppPack       |
| 财务全面预算（收入/支出沙盘推演）    | 应用包 #4（通用沙盘的第二个验证）  | 新增 AppPack       |
| 公务员班子配置（干部沙盘推演）      | 应用包 #5              | 新增 AppPack       |

**唯一需要重开插件的例外**（详见 §5）：需要独立部署/合规隔离、独立发布节奏与团队、或交互范式根本不同。这些都不是"新应用"的正常情况。

## 1. 能力分层：通用 vs 应用

### 1.1 三层能力模型

```
┌──────────────────────────────────────────────────────────┐
│ 应用层（App Pack）                                        │
│  安全 · 设备 · CRM · 财务预算 · 干部配置 · …              │
│  每个应用 = 本体类型 + 规则 + 状态模型 + 杠杆 + 视图      │
├──────────────────────────────────────────────────────────┤
│ 通用引擎层（Kernel，不含任何行业字面量）                   │
│  E1 本体引擎   ：类型注册 / 图存储 / 查询                  │
│  E2 规则引擎   ：约束与合规判定（AST 解释）                │
│  E3 评价引擎   ：多指标聚合 / 评分 / 分级                  │
│  E4 传导引擎   ：状态在图上传播 / 依赖重算                 │
│  E5 沙盘引擎   ：杠杆 → 传导 → 目标 的情景推演             │
│  V  可视化引擎 ：图谱 / 链路图 / 沙盘看板                  │
├──────────────────────────────────────────────────────────┤
│ 数据层：套件 · 图 · 规则包 · 模型参数 · 情景快照           │
└──────────────────────────────────────────────────────────┘
```

### 1.2 通用能力判定标准

一个能力进入内核，必须同时满足：

1. 不包含任何行业名词（无"安全""预算""干部"字面量）；
2. 至少 2 个应用能复用，或被明确规划为 2 个以上；
3. 可通过声明式配置表达差异，而非分支判断。

按此标准，四类能力明确属于内核：

| 通用能力     | 内核模块 | 安全       | 财务          | 干部         |
| -------- | ---- | -------- | ----------- | ---------- |
| 本体建模与图查询 | E1   | 设备/作业/法规 | 科目/成本中心/产品  | 岗位/人员/单位   |
| 约束与合规判定  | E2   | 法规条款     | 预算规则/内控     | 任职资格       |
| 多指标评价    | E3   | 四色评级     | 预算达成/利润率    | 班子适配度      |
| 状态传导     | E4   | 风险传播     | 收入→毛利→净利→现金 | 人员→岗位→班子效能 |
| 情景沙盘     | E5   | 新增作业影响   | 预算调整推演      | 干部调整推演     |
| 链路可视化    | V    | 事故根因链    | 偏差归因链       | 配置影响链      |

**"链路"在本方案中统一为三类**，共用一套渲染器：

| 链路类型 | 方向       | 用途     | 场景          |
| ---- | -------- | ------ | ----------- |
| 因果链  | 事件 → 原因  | 根因分析   | 事故调查、预算偏差归因 |
| 传导链  | 变更 → 受影响 | 影响面分析  | 风险传播、成本传导   |
| 依赖链  | 目标 ← 驱动  | 沙盘推演解释 | 利润驱动、班子效能驱动 |

### 1.3 现状差距

当前代码是"单应用硬编码"：实体/关系是封闭联合类型（[shared-types.ts](file:///g:/dsh-plugins/dsh-ontology/src/shared-types.ts#L5-L69)），双轴判定写死 PCF（[builtin-frameworks.ts](file:///g:/dsh-plugins/dsh-ontology/src/builtin-frameworks.ts#L29-L41)），评分只有"覆盖度"（[datastore.ts](file:///g:/dsh-plugins/dsh-ontology/src/datastore.ts#L704-L879)），无规则/传导/沙盘引擎。

**升级要做的不是加页面，而是把"应用"抽象出来。**

## 2. 平台架构

### 2.1 依赖规则（可强制校验）

```
应用包 ──> 域服务 ──> 内核端口
   │
   └──> 应用数据（JSON，只读声明）

合法：apps ──> kernel       ✅
禁止：kernel ──> apps       ❌ 内核不得出现 SAFETY_/BUDGET_/CADRE_ 等字面量
```

评审红线：`src/kernel/**` 不得 import `src/apps/**`；用 ESLint 规则或单测断言强制。

### 2.2 内核端口契约

```ts
interface Kernel {
  graph: GraphQueryPort        // 邻接/路径/子图/索引
  ontology: TypeRegistry       // 实体/关系类型注册与校验
  rules: RuleInterpreter       // 通用 AST 判定，输出证据
  score: ScorePipeline         // 组件注册 → 加权 → 分级
  propagate: PropagationEngine // 有向传导 + 聚合 + 封顶 + 环保护
  sandbox: SandboxEngine       // 杠杆 → 状态 → 目标
  chain: ChainBuilder          // 因果/传导/依赖三类链路
  store: SnapshotStore         // 套件/模型/情景快照
}
```

### 2.3 应用包契约

```ts
interface AppPack {
  id: string                       // 'chemical-safety' | 'finance-budget' | 'cadre-allocation'
  name: string
  ontology: { kinds: KindMeta[]; relations: RelationMeta[] }
  rules: RuleDoc[]                 // 通用 AST
  state: {
    variables: StateVariable[]     // 图上节点/边的状态量
    objectives: Objective[]        // 评价目标（可多个，带权重）
    grades: GradeScale[]           // 分级（四色/三级/…）
  }
  propagation: PropagationRule[]   // 传导方向 + 系数 + 聚合方式 + 封顶
  levers: Lever[]                  // 可调杠杆（沙盘输入）
  causeTaxonomy?: CauseTaxonomy     // 根因分类（可选，如人机料法环）
  views: ViewDeclaration[]         // 页面与可视化声明
}
```

**应用包以声明式 JSON 为主、策略代码为辅**：90% 的差异（类型、规则、权重、传导、视图）用配置表达；只有特殊计算（如 GB18218 R 值法）写为可注册的 `ScoreComponent` / `PropagationFn` 插件。

## 3. 通用沙盘模型（回应财务与干部）

安全评级、财务预算、干部配置看似无关，但都是同一结构：

```
给定一组杠杆（决策变量）
  → 沿图上的关系传导（传导规则）
  → 改变各节点状态（状态变量）
  → 聚合为若干目标（评价函数）
  → 与基线对比，输出推演结果与解释链路
```

### 3.1 四个通用构件

| 构件                   | 定义         | 安全             | 财务预算             | 干部配置           |
| -------------------- | ---------- | -------------- | ---------------- | -------------- |
| **状态变量** State       | 节点/边上的可计算量 | 风险分、合规率        | 收入、成本、毛利、现金流     | 岗位匹配度、班子结构指标   |
| **杠杆** Lever         | 可调整的输入     | 新增作业、措施落实、检验状态 | 单价、销量、编制、费用率     | 人员调整、提拔、交流     |
| **传导规则** Propagation | 状态如何沿边扩散   | 设备→装置→区域，短板封顶  | 销量→收入→毛利→净利→现金   | 人员→岗位→班子效能     |
| **目标函数** Objective   | 评价与分级      | 厂区安全指数（四色）     | 收入达成率、利润率、现金安全边际 | 班子适配度、结构合理性、风险 |

### 3.2 通用沙盘算法

```
1. 基线快照 baseline = evaluate(currentState)
2. 应用杠杆 scenario → factsDelta（不写库）
3. 反依赖索引展开受影响子图 dirty
4. 按拓扑序重算 dirty 上的状态与目标
5. 输出：
   - before / after / delta
   - 关键传导路径（top N）
   - 触发的规则与证据
   - 建议（可选，规则生成，非 LLM）
```

**统一伪代码**（三个应用共用）：

```ts
function simulate<K extends AppPack>(app: K, baseline: Snapshot, levers: LeverInput[]) {
  const facts = applyLevers(app, baseline.facts, levers)
  const dirty = reverseDeps.expand(facts.changedNodeIds)
  const order = topoSort(dirty)                       // 环 → 强连通分量折叠
  const after = recompute(app, order, facts)
  return {
    before: baseline.scores,
    after: after.scores,
    delta: diffScores(baseline.scores, after.scores),
    chains: app.chain.build('dependency', dirty, after),
    hits: diffRuleHits(baseline.hits, after.hits),
  }
}
```

## 4. 升级还是重开插件：决策依据

### 4.1 决策树

```
新增一个业务域
  ├─ 是否只是新的本体 + 规则 + 目标 + 视图？
  │     └─ 是 → 升级现有插件，新增 AppPack（默认路径）
  ├─ 是否需要独立部署 / 数据合规物理隔离？
  │     └─ 是 → 新建插件，复用 kernel 包
  ├─ 是否需要独立发布节奏 + 独立团队？
  │     └─ 是 → 新建插件，复用 kernel 包
  └─ 交互范式是否根本不同（实时协同/视频/硬件）？
        └─ 是 → 新建插件
```

### 4.2 依据

| 判断维度            | 升级（AppPack）   | 重开插件        |
| --------------- | ------------- | ----------- |
| 复用图/规则/传导/沙盘/渲染 | 100%          | 0%，需复制      |
| 数据一致性           | 单一事实源         | 两套数据，易不一致   |
| 交付复杂度           | 一个插件、一份安装     | 多插件、多入口、多版本 |
| 应用隔离性           | 靠模块边界         | 物理隔离        |
| 合规隔离            | 不满足           | 满足          |
| 独立发版            | 不支持（同包）       | 支持          |
| 新增应用成本          | 一套配置 + 少量策略代码 | 一次完整插件开发    |

**结论**：安全、设备、CRM、财务、干部都属于第一类，**升级，不重开插件**。只有当"合规隔离/独立团队/异构交互"出现时，才重开插件，且那时应把内核抽成共享包，而不是复制。

### 4.3 平台成熟度路线

| 级别        | 形态                 | 触发              |
| --------- | ------------------ | --------------- |
| L1（现状）    | 单应用，能力硬编码          | —               |
| L2（本方案目标） | 内核 + AppPack，配置驱动  | 安全应用落地 + 财务应用验证 |
| L3        | 应用可视化建模（低代码配本体/规则） | ≥3 个应用稳定运行      |
| L4        | 服务化 / 多租户          | 集团多厂区或对外交付      |

## 6. 首个应用：化工安全（核心闭环）

先做安全，因为它的规则最密、链路最复杂，能压测内核。

### 6.1 实体与关系

| 实体                | 关系              |
| ----------------- | --------------- |
| 法规 / 条款           | 法规→条款→适用对象→管控措施 |
| 区域 / 装置 / 设备 / 物料 | 区域→装置→设备→物料     |
| 作业 / 作业票          | 作业→区域/设备/危险源/票证 |
| 危险源 / 管控措施 / 检查项  | 措施→危险源；检查项→条款   |
| 事件                | 事件→位置/涉及对象/原因链  |

### 6.2 评级模型（四层正交，避免重复计分）

| 层                | 回答    | 作用对象     | 排除          |
| ---------------- | ----- | -------- | ----------- |
| A 固有风险（LEC）      | 本身多危险 | 作业/设备    | 不算存量、不算管控   |
| B 危险源规模（GB18218） | 体量多大  | 装置/危险源   | 不算作业频次、不算管控 |
| C 管控有效性（双重预防）    | 该做做到没 | 全部       | 只算偏差        |
| D 结构传播           | 如何放大  | 装置/区域/厂区 | 不产生新风险      |

```
A: D = L×E×C → 分段映射 0–100
B: Q = Σ(qi/Qi)，Q≥1 为重大危险源，R 值法分级 → 0–100
C: 100×(0.4×法规符合率 + 0.3×措施覆盖率 + 0.2×隐患整改率 + 0.1×票证合规率)
D: S_parent = Σ(w_i×S_child_i)/Σw_i；子含红→父≤59，子含橙→父≤74
融合：S = Σ(w_c×S_c)/Σw_c（仅适用分量），默认 A.35 / B.25 / C.30 / 指标.10
分级：红<60 ｜ 橙60–74 ｜ 黄75–89 ｜ 蓝≥90
```

**按实体限定适用分量**（去重执行点）：

| 实体    | A | B | C | 指标 |
| ----- | - | - | - | -- |
| 作业    | ✅ | ❌ | ✅ | ✅  |
| 设备    | ✅ | ✅ | ✅ | ✅  |
| 装置    | ❌ | ✅ | ✅ | ✅  |
| 区域/厂区 | ❌ | ❌ | ✅ | ❌  |

### 6.3 根因分析

```
① 事件种子 → ② 沿 CAUSED_BY 反向展开（深度≤5）→ ③ 挂屏障失效（预防/检测/缓解）
→ ④ 挂证据（条款/规则/属性异常）→ ⑤ 4M1E 归类 → ⑥ 排序
rankScore = Π(边置信度) × 后果严重度 × 可控性
```

无证据节点标 `unverified` 单列，不进入 Top，不臆造。

### 6.4 首期范围

`P0 内核契约` → `P1 最小数据底座` → `P2 评级` → `P3 根因链路`。法规与资产用样例打通，不做全量法规库。

## 7. 第二个应用：财务全面预算（验证平台通用性）

**为什么选财务做第二个**：纯数据、无物理约束、沙盘需求天然明确，最能验证"内核是否真的通用"。

* 本体：预算科目、成本中心、产品、客户、编制、期间

* 规则：预算刚性约束、内控审批、费用率红线

* 状态：收入 / 成本 / 毛利 / 净利 / 现金流

* 传导：销量→收入→毛利→净利→现金；科目→成本中心

* 杠杆：价格、销量、编制、费用率、投资节奏

* 目标：收入达成率、净利率、现金安全边际

* 链路：偏差归因链（收入未达 → 销量下降 → 客户流失 → …）

**验收标准**：财务应用**不修改内核代码**，仅新增 AppPack 即可跑通沙盘。若必须改内核，说明抽象不合格，回改内核。

> 干部配置应用同理验证：只新增 AppPack，验证"人岗匹配 + 班子互补"传导。

| **P1 安全数据底座** | 安全 AppPack、样例法规/厂区/作业、CSV 导入、图谱                            | 条款→对象→设备链路可走通            |
| **P2 安全评级**   | 规则解释器、四层评分、快照、扣分归因、评级页                                     | 分数可复现、可下钻、封顶生效           |
| **P3 安全根因**   | 因果引擎、链路渲染器、根因排序、证据                                         | ≥3 层链路、Top3 有证据、环/未验证正确  |
| **P4 通用沙盘**   | SandboxEngine + Lever/Propagation/Objective 通用化            | 安全场景推演跑通                 |
| **P5 财务验证**   | 财务 AppPack，不改内核                                            | 沙盘推演与归因链跑通               |
| **P6 干部验证**   | 干部 AppPack，不改内核                                            | 班子配置推演跑通                 |

**关键门禁**：P5/P6 若需改内核，暂停新增应用，先修抽象。

## 9. 质量保障

| 层次    | 手段                                              |
| ----- | ----------------------------------------------- |
| 内核通用性 | 单测断言 `src/kernel` 不 import 任何 app；内核仅依赖接口       |
| 引擎正确性 | 规则 AST 单测、评分边界值、传导环保护、沙盘增量一致性（全量重算 vs 增量重算结果一致） |
| 应用可复现 | 每个 AppPack 带黄金样例与期望输出快照                         |
| 回归    | PCF 现有行为快照测试                                    |
| 端到端   | 安全：导入→评级→推演→事件→根因；财务：预算→杠杆→推演→归因                |

## 10. 风险与边界

| 风险             | 对策                                  |
| -------------- | ----------------------------------- |
| 过度抽象，内核变"万能框架" | 内核只保留 5 个引擎；新能力先进应用包，2 个应用复用后才下沉    |
| 配置驱动导致难调试      | 每次评估输出 `modelVersion` + 完整中间量 + 证据链 |
| 评分权重主观         | 参数外置 + 版本留痕 + 专家校准 + 敏感性分析          |
| 财务/干部数据敏感      | 应用级数据分区；必要时按 §4.1 独立部署              |
| 安全责任边界         | 界面与报告注明"辅助决策，不替代法定安全评价"             |
| 旧数据迁移          | `appId` 缺省 pcf，零迁移                  |
